# tg-games — Telegram LLM RPG Bot

Текстовые RPG-игры в Telegram, где **каждый ход игрока обрабатывает LLM**.
Движок работает как редуктор: он не просто хранит текст, а валидирует и
обновляет JSON-состояние игры. Ход разделён на **пять независимых фаз**
(issue #65, #137): сперва LLM-рассказчик описывает, что произошло, затем
отдельные LLM-учётчики обновляют инвентарь, характеристики, флаги мира и
остальные данные под уже принятый нарратив — так на дешёвых моделях текст не
расходится с инвентарём, здоровьем и временем мира.

> ⚙️ **Schema Engine — единственный путь исполнения (issue #178, #238).**
> Начиная с issue #238 рантайм исполняет **все** типы запросов
> (`action`, `hint`, `support`, `illustration`) только через интерпретатор
> редактируемых схем (`executeSchema`, `packages/core/src/engine/schemaEngine.ts`). Хардкодный
> пайплайн и флаг `USE_SCHEMA_ENGINE` удалены. Описанные ниже «пять фаз» хода —
> это структура **дефолтной `action`-схемы** (узел нарратива + четыре узла
> состояния), которая сидируется миграцией и редактируется во вкладке «Схемы»
> админки. Если активной схемы нужного типа в БД нет, движок бросает
> `MissingActiveSchemaError`, и пользователю доставляется ошибка — «тихого»
> отката на старый код больше нет (мотивация: сбой должен быть виден, а не
> замаскирован). Каждое исполнение (успех и ошибка) пишется в
> `schema_execution_log`. Подробности и оставшиеся доработки —
> в [docs/schema-engine-gap-plan.md](docs/schema-engine-gap-plan.md).

> 🧠 **Рассуждающая суб-схема генерации нарратива (issue #317).** Концептуальный
> апгрейд фазы нарратива из одного промпта в изолированную суб-схему рассуждения
> «анализ критериев строгости → черновик ↔ критик духа жестокого мира» (выход из
> цикла — по оценке критика, а не по счётчику) плюс продвинутая БЗ («конституция
> духа мира» вместо плоского Vector RAG). Аналитический обзор, проверенный
> исполняемым примером (`examples/narrative-reasoning-subschema.json`), и этапный
> план интеграции — в
> [docs/narrative-reasoning-subgraph-plan.md](docs/narrative-reasoning-subgraph-plan.md).

```
[Действие игрока] + [Текущий JSON состояния + время мира]
            │
            ▼
   [Фаза 1 · LLM-рассказчик] ─ нарратив по правилам мира и времени, без счёта чисел
            │
            ▼
   [Фаза 2 · инвентарь]
            │
            ▼
   [Фаза 3 · характеристики]
            │
            ▼
   [Фаза 4 · флаги мира]
            │
            ▼
   [Фаза 5 · остальные данные: location, world_time, character.hp]
            │
            ▼
[Валидация JSON по схеме] ➔ [Жёсткая санитизация лимитов] ➔ [Запись JSON в БД] ➔ [Ответ игроку]
```

## Возможности

- 🎲 Игровой движок-редуктор с обновлением JSON-состояния через LLM.
- 🎬 **Двухфазный оркестратор хода** (issue #65): отдельный промпт-рассказчик
  генерирует нарратив по правилам мира, отдельный промпт-учётчик пересчитывает
  состояние строго под принятый нарратив. На дешёвых моделях это убирает
  расхождение между текстом и инвентарём/HP/навыками.
- 🕰 **Время мира** (issue #65): сезон, календарная дата и время суток входят в
  состояние, учитываются при генерации нарратива (погода, темнота, доступность
  людей и ресурсов) и аккуратно продвигаются вперёд при учёте состояния.
- 📚 **Экспертиза в игре через эмбеддинги** (issue #154): перед фазой нарратива
  добавлена **фаза 0** — отдельный дешёвый LLM-запрос выделяет ключи ситуации
  хода (`{"keys": [...]}`); по их эмбеддингам (`EMBEDDING_MODEL`, pgvector)
  подтягиваются до `GAME_EXPERTISE_TOP_K` справочных документов базы знаний
  именно этой игры и подставляются в промпт нарратива (плейсхолдер
  `{{expertise}}`). Это разгружает системный промпт от ситуативных правил быта:
  длинные детали мира хранятся документами и подмешиваются только когда
  релевантны. Документы привязываются к игре в разделе «Экспертиза» админки;
  стартовый набор для «Выживания бомжа» (`game_id = bomj`) сидируется при запуске.
  Механизм полностью опционален: без настроенного провайдера эмбеддингов или при
  `GAME_EXPERTISE_TOP_K=0` фаза 0 пропускается и ход идёт по прежнему 5-фазному
  пути.
- 🧠 **Долговременная память игры** (issue #166): важные факты о ходе игры и
  состоянии мира (обещания, союзы, необратимые события) живут в ячейках БД
  (таблица `game_memory_cells`, по сессии) и при необходимости подключаются к
  промптам. После учёта состояния добавлена **финальная фаза** — отдельный
  дешёвый LLM-запрос («хронист») выделяет новые важные факты хода и складывает их
  в память; на каждом ходе самые важные ячейки подставляются в промпт нарратива
  (плейсхолдер `{{memory}}`). В отличие от экспертизы память **не использует
  эмбеддинги**: отбор детерминированный (по важности, затем по свежести, до
  `GAME_MEMORY_TOP_K` ячеек). Один рубильник `GAME_MEMORY_TOP_K`: `> 0` включает
  и подстановку, и извлечение; `0` — отключает. Извлечение работает в режиме
  best-effort (сбой фазы не ломает ход) и учитывается в аудите стоимости LLM, а
  при отмене хода (`/cancel`) факты этого хода удаляются из памяти в той же
  транзакции.
- 🧩 Мульти-провайдерная абстракция LLM (паттерн «Стратегия»): **OpenAI**,
  **Google Gemini**, **OpenRouter**, **Azure OpenAI** — все в JSON Mode.
- 🛡 Манифесты сценариев (`worldRules`, лимиты) + защитный промпт-фильтр
  против читерства и «жёсткая» валидация на стороне Node.js.
- 🎭 Пресеты персонажей (имя, описание, инвентарь, навыки) и стартовых локаций
  (с вводным нарративом) в каждом манифесте — выбираются перед началом игры.
- ⭐️ Покупка игр за **Telegram Stars** (`sendInvoice` → `pre_checkout_query`
  → `successful_payment`).
- 🛟 **Служба поддержки** (issue #57): отдельные боты для клиентов и
  администраторов. Сообщения клиента складываются в обращения («топики»),
  администраторы получают уведомления о новых обращениях и отвечают клиенту
  прямо из чата. Команда `/users` (issue #62) даёт админу просмотр пользователей,
  их игр и скачивание истории ходов файлом — всё через inline-меню с пагинацией.
- 🤖 **LLM-консультант первой линии** (issue #59): «Бот СП» сначала консультирует
  клиента и собирает детали проблемы, а когда сведений достаточно — передаёт
  обращение администратору со скомпилированным описанием. Сообщения помечаются
  «🤖 Бот СП» (консультант) или «💬 Служба поддержки» (ответ администратора).
- 🔊🎨 **Озвучка и иллюстрация сцены** (issue #71): под сообщением-результатом
  хода появляются две inline-кнопки «🔊 Озвучить» и «🎨 Нарисовать иллюстрацию».
  По клику исчезает именно нажатая кнопка, а игроку приходит **новое** сообщение
  с голосовой озвучкой сцены (TTS) или сгенерированной картинкой. Возможность
  необязательна (провайдеры **OpenAI**/**Google**, флаги `MEDIA_*`): без ключа
  кнопки не показываются и текстовая игра работает как прежде.
- 🎙️ **Голосовой ввод действий** (issue #118): если у игрока есть активная игра,
  присланное голосовое сообщение распознаётся в текст (STT) и выполняется как
  игровое действие — отвечать можно голосом, не печатая. Аудио **нигде не
  сохраняется**: буфер живёт только в памяти на время распознавания. Возможность
  необязательна (провайдеры **OpenAI**/**Google**, флаги `MEDIA_STT_*`): при
  выключенном STT бот просит написать действие текстом.
- ⚙️ **Пользовательские настройки медиа** (issue #81): команда `/config`
  открывает inline-меню выбора озвучки или иллюстраций, затем модели и параметра
  (голос TTS или размер/соотношение изображения). Провайдера выбирает только
  проект через `MEDIA_PROVIDER`; игрок настраивает значения в рамках этого
  провайдера. Без пользовательской настройки используются значения из `.env`.
- 🧪 **Отчёт тестировщику по медиа** (issue #75): пользователю с флагом
  `is_tester` следом за озвучкой или иллюстрацией приходит технический отчёт —
  переданный запрос (провайдер, модель, параметры, вход), полученный ответ,
  расход токенов (если провайдер его сообщает) и текст ошибки API, если вызов
  упал. Обычные игроки отчётов не видят.
- 🖥 **Web-админка** (issue #114): приложения `apps/admin-api/` (NestJS API) и
  `apps/admin-web/` (Vite + React). Вход выполняется через одноразовый код, который
  админский Telegram-бот отправляет пользователю с `is_admin = TRUE`.
  В интерфейсе доступны пользователи, сессии с фильтрами и логом ходов, игры,
  группы, шаблоны промптов, глобальные модели, обращения поддержки и алиасы моделей Azure.
- 🔗 **URL-навигация в админке** (issue #152): раздел, выбранная сущность и
  фильтры кодируются в hash-маршруте вида `#/topics/abc-123?status=open`.
  Закладки и расшаренные ссылки воспроизводят страницу, кнопки браузера
  «Назад»/«Вперёд» работают, а обновление страницы не сбрасывает состояние.
  Маршрутизация вынесена в `apps/admin-web/src/adminRoute.ts` (чистые
  `parseRouteHash`/`buildRouteHash` плюс хук `useHashRoute` на History API).
- 🧩 **Подсказка подстановок шаблонов в админке** (issue #142): в редакторе
  раздела «Шаблоны промптов» под полем текста выводится список доступных для
  выбранного промпта подстановок `{{...}}` с пояснением, что подставляется
  вместо каждой. Состав подстановок задан в TS (`apps/admin-web/src/promptVariables.ts`)
  и держится синхронным с builder'ами промптов на сервере.
- 🔷 **Алиасы моделей Azure в админке** (issue #124): раздел «Azure» показывает
  таблицу `azure_models` (deployment → каноническая модель) и позволяет
  добавлять новые алиасы, редактировать каноническую модель существующих и
  удалять их. Карта алиасов нужна, чтобы по имени deployment в Azure найти цену
  модели в справочнике и посчитать стоимость хода.
- 🧠 **Лог LLM-запросов в админке** (issue #122): раздел «LLM запросы» показывает
  историю обращений к моделям из таблицы `llm_request_logs` с фильтрами по сессии
  игры, пользователю (`user_id`/telegram id), типу запроса и признаку ошибки.
  По каждой записи доступна детальная карточка: провайдер, модель, параметры,
  использованные токены и стоимость, полный текст запроса, ответа и ошибки.
  Перейти к запросам конкретной сессии или пользователя можно из их карточек.
- 🎛 **Глобальные модели по умолчанию** (issue #345): раздел «Модели» в админке
  задаёт одну default-модель для всех LLM-запросов и одну default-модель для
  эмбеддингов. Провайдеры по-прежнему берутся из `.env`
  (`LLM_PROVIDER` / `EMBEDDING_PROVIDER`), а имена моделей хранятся в таблице
  `model_defaults` и кешируются с TTL (`MODEL_DEFAULTS_CACHE_TTL_MS`, по
  умолчанию 30 секунд), поэтому бот подхватывает изменения автоматически.
- 🕮 **История версий манифестов** (issue #125): при каждом изменении манифеста
  игры прежняя версия сохраняется в таблицу `game_manifest_history`. На странице
  игры правее заголовка формы отображается число сохранённых версий и селектбокс с
  датами — выбор прошлой версии открывает её во всплывающем окне для просмотра.
  (Тексты промптов теперь живут в схемах Schema Engine — см. вкладку «Схемы» с
  собственными историей версий и импортом/экспортом.)
- 📤 **Импорт и экспорт манифестов** (issue #133): список «Игры» в web-админке
  позволяет скачать полный JSON-файл и импортировать его обратно. Импорт добавляет
  новые записи и обновляет существующие без удаления отсутствующих; прежние версии
  изменённых записей сохраняются в историю.
- 🧾 **Выгрузка экспертизы и аналитика поисковых запросов** (issue #156): на
  странице «Документы экспертизы» появились кнопки экспорта и импорта всей базы
  документов в JSON (импорт сопоставляет записи по паре «заголовок + игра»,
  пересчитывая эмбеддинги поисковых фраз). Вторая вкладка «Поисковые запросы»
  показывает журнал прошлых обращений к экспертизе (введённая фраза, область,
  лучшее совпадение, число найденных документов) с фильтрами по области, по дате
  («раньше чем»), по качеству лучшего совпадения (удачные / ничего не нашедшие) и
  семантическим поиском по фразе (эмбеддинг запроса и сортировка по косинусной
  близости). Текущую выборку можно выгрузить в JSON. Каждый поисковый запрос
  экспертизы (в боте и в игре) сохраняется в таблицу `expertise_search_queries`
  лучшим усилием — сбой записи журнала не прерывает консультацию или ход.
- 🗄 Хранение в **PostgreSQL** (`users`, `user_media_configs`,
  `game_sessions`, `game_steps`, `payment_logs`, `support_tickets`, `support_messages`,
  `support_admin_ticket_reads`, `game_manifest_history`,
  `model_defaults`, `azure_models`, `expertise_documents`, `expertise_document_embeddings`,
  `expertise_search_queries`).
- 🐳 Развёртывание через **Docker Compose**.

## Структура проекта

Проект — монорепозиторий на npm workspaces (issue #269): переиспользуемые
библиотеки лежат в `packages/*`, запускаемые приложения — в `apps/*`, единый
`package-lock.json` и общий граф зависимостей в корне.

```
packages/
├── core/                    @tg-games/core — общая бизнес-логика ядра
│   └── src/
│       ├── config.ts        загрузка и валидация переменных окружения
│       ├── types.ts         типы GameState / WorldTime / LLM-ответы фаз
│       ├── games/manifests.ts типы манифестов и сборка стартового состояния
│       ├── llm/             единый интерфейс провайдера, фабрика по LLM_PROVIDER, провайдеры OpenAI / Google / OpenRouter / Azure
│       ├── media/           озвучка и иллюстрации сцены (issue #71): интерфейс, фабрика, WAV, провайдеры
│       ├── engine/          Schema Engine: schemaEngine.ts (executeSchema), promptTemplates, prompts, validation, reducer
│       └── db/              schema.sql, пул, migrate.ts, репозитории users / sessions / steps / payments / support
└── schema-contract/         @tg-games/schema-contract — единый контракт графа Schema Engine для 3 слоёв
    ├── index.mjs            источник правды (ESM); index.cjs генерируется из него
    └── build.mjs            генератор index.cjs (npm run build:contract)
apps/
├── bot/                     @tg-games/bot — три Telegram-бота (issue #57, #59)
│   └── src/
│       ├── index.ts         точка входа: запуск игрового бота (миграции БД — отдельным шагом, см. ниже)
│       ├── bot/             игровой бот: команды, меню, платежи, обработка действий, формат, эфемерное состояние
│       ├── botSupport/      клиентский бот поддержки: приём сообщений, «Бот СП» первой линии, передача админам
│       └── botSupportAdmin/ бот администраторов поддержки: /topics, /users, обращения, ответы клиенту
├── admin-api/               @tg-games/admin-api — NestJS API web-админки (issue #114)

│       ├── auth/            вход по коду из Telegram-бота и Bearer-сессии

└── admin-web/               @tg-games/admin-web — Vite + React web-админка (issue #114)
    └── src/                 интерфейс с верхним меню, таблицами, фильтрами и редакторами
```

приложения (`packages/core/tests/`, `apps/bot/tests/`, `apps/admin-api/tests/`,
`apps/admin-web/tests/`, `packages/schema-contract/tests/`).

## Движок: пятифазный оркестратор и время мира (issue #65, #137)

> **Schema Engine (issue #168, #238).** Описанные ниже фазы — это семантика
> **дефолтной схемы `action`**, а не хардкод. С issue #238 единственный путь
> исполнения всех четырёх типов запросов (`action`, `hint`, `support`,
> `illustration`) — редактируемые графы Schema Engine: фазы хода собраны из узлов
> графа (`llm_request`, `game_state_write`, `game_memory_write` и т. д.), который
> можно менять в админке без правки кода. Подробности архитектуры, формата графа,
> каталога узлов и поведения «нет активной схемы → ошибка» — в разделе
> [Schema Engine: редактируемые графы исполнения](#schema-engine-редактируемые-графы-исполнения-issue-168-238).

Чтобы на дешёвых моделях (например, `gpt-…-nano`) сгенерированный текст не
расходился с фактическими изменениями инвентаря и мира, обработка хода разделена
на пять независимых LLM-фаз с собственными системными промптами и собственным
бюджетом ретраев (`reducer.ts`, `processTurn`):

1. **Нарратив** (`buildNarrativeSystemPrompt` / `buildNarrativePrompt`). Модель в
   роли строгого рассказчика описывает, *что произошло* по правилам мира
   (`worldRules`) и с учётом времени мира, защищаясь от читерства. Числа здесь не
   считаются; ответ — только `{ "narrative": "…" }`.
2. **Инвентарь** (`buildInventorySystemPrompt` / `buildInventoryPrompt`).
   Модель возвращает только полный актуальный `inventory`.
3. **Характеристики** (`buildCharacteristicsSystemPrompt` /
   `buildCharacteristicsPrompt`). Модель обновляет устойчивые параметры
   персонажа: `skills` и `max_hp`. Текущий HP считается отдельно.
4. **Флаги** (`buildFlagsSystemPrompt` / `buildFlagsPrompt`). Модель обновляет
   только устойчивые булевы факты `world_flags`.
5. **Остальные данные** (`buildOtherStateSystemPrompt` /
   `buildOtherStatePrompt`). Модель обновляет `location`, `world_time`,
   `character.hp` и прочие поля, не выделенные в предыдущие фазы.

Эти пять обязательных фаз при необходимости обрамляются двумя опциональными.
Перед нарративом — **фаза 0 экспертизы** (issue #154): по ключам ситуации
подтягиваются справочные документы базы знаний (плейсхолдер `{{expertise}}`).
После учёта состояния — **финальная фаза памяти** (issue #166,
`buildMemorySystemPrompt` / `buildMemoryPrompt`): модель в роли «хрониста»
выделяет новые важные факты хода (обещания, союзы, необратимые события) и
возвращает `{ "memory": [{ "content", "category", "importance" }] }`. Факты
сохраняются в ячейки БД (`game_memory_cells`), а на каждом ходе самые важные из
них (до `GAME_MEMORY_TOP_K`, отбор детерминированный — по важности, затем по
свежести, **без эмбеддингов**) подставляются в промпт нарратива (плейсхолдер
`{{memory}}`). Фаза памяти работает в режиме best-effort: её сбой не срывает ход.
Оба обрамления включаются своими рубильниками (`GAME_EXPERTISE_TOP_K`,
`GAME_MEMORY_TOP_K`); при `0` соответствующая фаза пропускается.

**Граф знаний и Graph RAG (issues #323, #328, #334, #386).**
Помимо векторного поиска документов (`knowledge_query`) проект хранит знания мира
как типизированный ориентированный граф в Neo4j: концепты (вершины) и связи
(`OntologyConcept` и `ONTOLOGY_RELATION`). Граф наполняется вручную через раздел
**«Онтология»** в веб-админке или автоматически из документов экспертизы:
разовая LLM-индексация превращает абзацы прозы в концепты и связи с происхождением
`extracted`, которые ложатся рядом с ручными `authored`.

Поверх связного графа считаются **сообщества** (кластеры концептов) с короткой
LLM-сводкой каждого. Эти сводки нужны для обзорных вопросов о мире («что вообще
опасно зимой?»), на которые точечный поиск по документам отвечает слабо. Горячий
путь хода не обязан делать LLM-индексацию: извлечение графа и сводки выполняются
offline, а runtime должен только читать готовый графовый контекст.

Публичный узел агентного графового ретрива — `graph_rag`. Его внутренний
`graph_query` доступен только внутри `bodyGraph`, читает Neo4j по id или
embedding-ключам и возвращает компактные концепты с соседями. `graph_rag`
итеративно уточняет запрос, критикует найденный контекст и завершается по пустому
списку дополнительных вопросов или по `maxIterations`. Полное ТЗ — в
[docs/agentic-graph-rag-spec.md](docs/agentic-graph-rag-spec.md).

| Критерий | Vector RAG (#154) | Ручной граф (#323) | **Graph RAG (#328, #334, #386)** |
| --- | --- | --- | --- |
| Источник знаний | абзацы прозы | ручная разметка концептов | **автоизвлечение** из абзацев |
| Выборка | top-K по косинусу | графовые связи | agentic lookup **+ дополнительные вопросы** |
| Обзорные вопросы о мире | нет | слабо | **да** (сводки сообществ) |
| Наполнение | написал абзац | ручная разметка графа | **разовая LLM-индексация** абзацев |
| Объяснимость | число-расстояние | путь по графу | путь по графу **+ провенанс документа** |
| Зависимость от эмбеддингов | жёсткая | нет (опц.) | нужна для ключей вершин и первичного lookup |
| Главный риск | близость ≠ релевантность | неполнота ручного графа | шум извлечения (→ верификация) |

**Когда что выбирать.** Подходы дополняют друг друга и сосуществуют на одном
графе: ручные `authored`-связи (#323) задают каркас «духа мира», автоизвлечённые
`extracted`-связи (#328) насыщают его из документов, сводки сообществ дают обзор,
а Vector RAG (#154) остаётся фолбэком для точечных фактов и при пустом графе.
Деградация корректная: нет графа → Vector RAG; нет сводок → только локальный lookup.
Извлечённые концепты и связи помечаются происхождением и проходят **верификацию**
в админке (бейдж источника «вручную»/«извлечено» и кнопка «Подтвердить» на вкладках
«Концепты»/«Связи», отдельная вкладка «Сообщества» со сводками кластеров).
Подробности и план — в [docs/graph-rag-plan.md](docs/graph-rag-plan.md).

Если любая из обязательных фаз не вернула валидный JSON за отведённые попытки,
состояние **не меняется** и игрок получает сообщение о «нестабильном мире». Все фазы пишут в
общий лог LLM-запросов, поэтому стоимость хода считается по сумме всех вызовов.
Каждый фактический запрос к модели дополнительно сохраняется в таблицу
`llm_request_logs`: там есть тип запроса (`request_kind`), провайдер, модель,
параметры модели, текст запроса/ответа, токены и стоимость в миллицентах.
В аудит попадают нарратив, четыре подфазы учёта состояния мира, извлечение
долговременной памяти, подсказки, консультации службы поддержки, озвучка и
генерация иллюстраций.

**Время мира** (`WorldTime`: `season`, `date`, `time`, `time_of_day`) хранится
прямо в `GameState.current_state`. Стартовое время задаётся в манифесте сценария
(`startTime`), учитывается фазой нарратива (погода, темнота, доступность людей) и
тщательно продвигается фазой остальных данных. Точное время суток (issue #67) хранится в
поле `time` в формате **ЧЧ:ММ**: учётчик оценивает длительность действия в
минутах (короткая реплика — 1–5 мин, обыск/готовка — 10–40 мин, дорога — 30–120
мин, сон — до утра) и сдвигает часы вперёд; при переходе через полночь
увеличивается календарная дата. Текстовое `time_of_day` выводится из часов
детерминированно (ночь 22:00–04:59, утро 05:00–11:59, день 12:00–16:59,
вечер 17:00–21:59), поэтому два поля никогда не расходятся. Старые сессии из БД
без `world_time` или без `time` нормализуются на лету (`ensureWorldTime`), а
пропущенное моделью время сохраняется между ходами (`mergeWorldTime`) — никакой
миграции БД не требуется, так как состояние хранится в JSONB. Текущее время мира
видно игроку в разделе **Статус** в формате «08:00 (утро), 14 октября, осень».

## Schema Engine: редактируемые графы исполнения (issue #168, #238)

**Schema Engine** — это интерпретатор графов, заменивший хардкодный LLM-пайплайн.
Каждый из четырёх типов запросов (`action`, `hint`, `support`, `illustration`)
исполняется как граф из типизированных узлов, который хранится в БД и
редактируется во вкладке **Схемы** web-админки. Кода для конкретной фазы хода или
формата подсказки больше нет — поведение целиком задаётся графом, поэтому оператор
меняет логику игры без передеплоя.

### Архитектура

Единый контракт графа лежит в пакете `@tg-games/schema-contract` и используется
тремя слоями без дублирования:

- **движок** (`packages/core/src/engine/schemaEngine.ts`) — исполняет граф в рантайме;
- **backend** (`apps/admin-api/src/admin/`) — валидация, сохранение, import/export,
  test-run;
- **frontend** (`apps/admin-web/src/SchemasView.tsx`) — визуальный редактор на
  React Flow.

Интерпретатор `executeSchema(graph, ctx)` (`packages/core/src/engine/schemaEngine.ts`):

1. валидирует граф контрактом `validateSchemaGraphContract` (те же коды ошибок,
   что и при сохранении в админке);
2. инициализирует переменные схемы в контекст исполнения;
3. идёт по **exec-портам** от узла `start`, складывая исходящие связи в очередь;
   узел `merge` ждёт прихода всех своих exec-входов;
4. **data-порты** разрешаются лениво: значение входа узла вычисляется только в
   момент обращения, поднимаясь по связям до источника (узлы без exec-портов,
   например `transform`, исполняются по требованию).

Любая ошибка узла оборачивается в единый формат с полями `nodeId`, `nodeType`,
`message` и `lastRaw` (сырой ответ LLM для диагностики), что позволяет подсветить
упавший узел в редакторе и записать причину в аудит.

### Формат графа (graph JSON)

Граф сериализуется в JSON и хранится в колонке `schemas.graph_json` (типы — в
`packages/schema-contract/index.d.ts`):

```jsonc
{
  "version": 1,
  "schemaType": "action",        // action | hint | support | illustration
  // ↑ ровно одно из двух: пайплайн-схема несёт schemaType, суб-схема — subSchemaClass
  // "subSchemaClass": "common", // game | support | common (см. раздел «Суб-схемы»)
  "slug": "action",
  "gameId": null,                 // null — глобальная схема, иначе привязка к игре
  "variables": {},                // именованные переменные схемы
  "nodes": [
    {
      "id": "start",
      "type": "start",
      "position": { "x": 0, "y": 0 },
      "config": {}
    }
    // ...
  ],
  "edges": [
    {
      "id": "e1",
      "from": "start", "fromPort": "exec",   // источник: узел + порт
      "to": "llm",     "toPort": "exec"       // приёмник: узел + порт
    }
    // ...
  ]
}
```

Связи делятся на **exec** (порядок исполнения) и **data** (передача значений
между типизированными портами). Совместимость портов проверяется контрактом ещё в
редакторе.

### Каталог узлов

| Узел | Назначение |
| --- | --- |
| `start` / `end` | вход/выход графа: подача входных данных и сбор результата |
| `llm_request` | запрос к LLM с именованными входами и JSON-выходами; число ретраев задаётся полем `retries` |
| `knowledge_query` | семантический поиск документов экспертизы по ключам (RAG) |
| `game_memory_read` / `game_memory_write` | чтение и запись долговременной памяти игры |
| `manifest` | чтение полей манифеста сценария; в суб-схеме работает на манифесте вызывающей игры и не требует привязки к конкретной игре |
| `game_state_read` / `game_state_write` | чтение полного состояния и глубокий мерж изменений |
| `support_history_read` | история переписки тикета как массив реплик `{role, message}` (роли `bot`/`operator`/`user`; только схема `support`) |
| `game_history_read` | история ходов игры как массив реплик `{role, message}` (роли `master`/`player`; схемы `action`/`hint`/`illustration`) |
| `condition` | ветвление exec-потока по логическому условию |
| `variable_read` / `variable_write` | чтение и запись именованных переменных схемы |
| `loop` | цикл: счётчик `maxIterations` или итерация по массиву (`iterateItems`); агрегация результатов `aggregate: collect \| last`, в теле доступны `loopIndex`/`loopItem` |
| `transform` | пользовательский JavaScript в изолированной песочнице `node:vm` с таймаутом `SANDBOX_TIMEOUT_MS = 1000` мс (бесконечный цикл доставляет ошибку, а не вешает процесс) |
| `merge` | синхронизатор: ждёт нескольких exec-входов |
| `sub_schema` | вызов суб-схемы — inline-граф или подгрузка по `schemaSlug` с изоляцией контекста (свои `variables`/`nodeOutputs`); порты узла берутся из граничных портов суб-схемы (см. раздел «Суб-схемы») |
| `media_generate` | генерация иллюстрации через медиа-провайдер; при `canDraw` отдаёт бинарное изображение, иначе — текст промпта |
| `log` | запись входов узла в журнал исполнения (отладка) |

### Суб-схемы и классы (issue #310)

Суб-схема — самостоятельная переиспользуемая схема, которую вызывают из узла
`sub_schema` другой схемы. В отличие от пайплайн-схемы (`action`/`hint`/
`illustration`/`support`), она несёт не `schemaType`, а **класс** `subSchemaClass`
и хранится в колонке `schemas.schema_class`. Граф задаёт **ровно одно** из двух
полей — `schemaType` или `subSchemaClass` (XOR-инвариант, проверяется контрактом и
ограничением БД `num_nonnulls(schema_type, schema_class) = 1`).

Классы и их доступность:

| Класс | Палитра узлов | Откуда можно вызвать |
| --- | --- | --- |
| `game` (Игровая) | игровые узлы (чтение/запись состояния и истории игры) | только из игрового домена — схем `action`/`hint`/`illustration` или игровых суб-схем |
| `support` (Поддержка) | узлы поддержки (история переписки тикета) | только из домена поддержки — схемы `support` или support-суб-схем |
| `common` (Общая) | пересечение палитр `game` и `support` (узлы без привязки к домену) | отовсюду |

Несовместимый по классу вызов **не подключается** (резолвер возвращает `null`, а
движок бросает ошибку «активная схема не найдена») — «тихого» fallback нет.

**Граничные порты.** Входы и выходы суб-схемы настраиваются на её узлах `start` и
`end`: `start.config.outputs` задаёт входы суб-схемы, `end.config.inputs` — её
выходы. Каждый граничный порт — это `{ id, label, type }`, где `type` — любой
тип порта кроме `exec`, а `id` соответствует шаблону `^[A-Za-z0-9_]{1,40}$`. Узел
`sub_schema`, вызывающий суб-схему, показывает именно эти порты: при выборе суб-
схемы редактор кэширует их снимок в `node.config.ports`, а при встроенном графе
(`node.config.graph`) порты берутся из его узлов `start`/`end`.

**Манифест в суб-схеме.** Узел `manifest` внутри суб-схемы читает манифест
**вызывающей** игры (он передаётся из корневого контекста исполнения), поэтому
суб-схему не нужно привязывать к конкретной игре — одна общая суб-схема работает
для всех игр, которые её вызывают.

**Контекст выполнения при тестировании (issue #351).** Суб-схема исполняется не
сама по себе, а внутри домена вызывающей стороны, поэтому окно теста суб-схемы
(кнопка «Тест» в редакторе) позволяет задать этот **контекст выполнения**:

- для общей (`common`) суб-схемы оператор выбирает класс домена — «Поддержка» или
  «Игра»;
- для класса «Игра» (как у выбранного контекста, так и у `game`-суб-схемы)
  дополнительно выбирается конкретная игра — её манифест подгружается в тест;
- у `support`-суб-схемы контекст зафиксирован доменом поддержки.

Выбранный контекст уходит на `POST /api/schemas/:slug/test` как поле `context`
(`support`/`game`) и подменяет `callerKind`: по нему резолвятся вложенные
суб-схемы (общая суб-схема в контексте «Игра» видит игровые суб-схемы) и
подбираются дефолты экспертизы. Для пайплайн-схем контекст не запрашивается —
их домен задан типом схемы.

**Область экспертизы `knowledge_query` в суб-схеме (issue #353).** Узел
`knowledge_query` ищет либо в документах поддержки (`game_id IS NULL`), либо в
экспертизе игры (`scope { gameId }`). Пайплайн-схема несёт об этом собственный
`schemaType`, а суб-схема — нет, поэтому область берётся из домена вызывающей
стороны (`expertiseDomain` в контексте исполнения). Контекст наследуется
вложенными суб-схемами, так что `knowledge_query` внутри них ищет в правильной
области и в боевом рантайме поддержки, и при тесте. Раньше суб-схема всегда
уходила в экспертизу игры: тест общей суб-схемы в контексте «Поддержка» возвращал
пустой результат, хотя тот же запрос в пайплайн-схеме поддержки находил документ.

**Переменные черновика при тестировании (issue #355).** Тест прогоняется на
черновике, если он есть (issue #286), но именованные переменные схемы (`variables`)
по ошибке инициализировались из рабочей версии — поэтому изменения переменных в
черновике суб-схемы игнорировались, и по факту тест шёл по рабочей версии. Теперь
переменные берутся из того же графа, что и исполняется: при тесте черновика — из
черновика, иначе — из рабочей версии.

**Фиксация черновика перед тестом (issue #355).** Сервер прогоняет тест по
черновику из БД (`row.draft_graph_json ?? row.graph_json`), но кнопка «Тест»
открывала модалку, не сохранив несохранённые правки редактора как черновик. Из-за
этого тест суб-схемы черновика по факту шёл по последней сохранённой (рабочей)
версии: удалённый в редакторе узел (например, `constant-1`) всё ещё исполнялся.
Теперь перед открытием теста несохранённые правки автоматически фиксируются как
черновик (как и при переключении схемы, issue #286), поэтому тест всегда прогоняет
ровно то, что показано в редакторе.

### Поведение при отсутствии активной схемы

Legacy-пайплайн и флаг `USE_SCHEMA_ENGINE` удалены (issue #238): «тихого» отката
на старый код больше нет. Если активной схемы нужного типа в БД нет,
`getActiveSchema` возвращает `null`, рантайм бросает `MissingActiveSchemaError`, и
**ошибка доставляется пользователю** вместо незаметной подмены поведения:

- ход и подсказка — сообщение `SCHEMA_UNAVAILABLE_TEXT` (`apps/bot/src/bot/bot.ts`),
  прогресс-индикатор снимается, LLM не вызывается;
- поддержка — сообщение об ошибке клиенту (`apps/bot/src/botSupport/bot.ts`);
- иллюстрация — ошибка вместо картинки, кнопка повтора восстанавливается
  (`packages/core/src/media/illustrationSchema.ts`).

Каждая попытка (успех и сбой) фиксируется в таблице `schema_execution_log`
(`logSchemaExecution`): `schema_slug`, `game_id`, `session_id`, входы/выходы,
лог LLM-запросов и длительность.

### Операционные сценарии

Все операции доступны во вкладке **Схемы** админки и через Admin API
`/api/schemas/*` (под `AdminAuthGuard`):

- **Активные схемы.** На пару `(slug, game_id)` допустима только одна активная
  версия (`idx_schemas_active_unique`). Глобальная схема (`game_id = null`)
  применяется ко всем играм; схема с конкретным `game_id` имеет приоритет
  (`getActiveSchema` сначала ищет схему игры, затем глобальный fallback).
- **Выбор области схем** (issue #234). Слева от кнопок типа схемы во вкладке
  **Схемы** стоит селектбокс области: **🛟 Поддержка** (открыта по умолчанию),
  **🌐 Базовая (для всех игр)** — глобальные схемы `game_id = null` — и список
  **🎮 игр** (`GET /api/games`). При выборе игры по умолчанию открывается тип
  **«Действие»**; типы `action`/`hint`/`illustration` редактируются для каждой
  игры отдельно, а `support` остаётся глобальной. Если у игры нет своей схемы,
  показывается унаследованная базовая с подсказкой — сохранение создаст схему
  именно этой игры (`PATCH` с `gameId`). Выбранная область отражается в пути
  браузера (`#/schemas/:slug?gameId=…`), поэтому конкретную схему можно открыть
  из закладки или по ссылке.
- **Сохранение версии** (`PATCH /api/schemas/:slug`). Перед записью граф
  валидируется тем же контрактом, что и в рантайме; прежняя активная версия
  архивируется в `schema_history`.
- **История и restore** (`GET /api/schemas/:slug/history`,
  `POST /api/schemas/:slug/restore/:historyId`). Любую архивную версию можно
  сделать активной снова — текущая при этом уходит в историю.
- **Test-run** (`POST /api/schemas/:slug/test`). Прогон на **том же**
  `executeSchema`, что и продакшен: возвращает `outputs`, `llmLog`, `durationMs`
  и `costMillicents`, а при сбое — `nodeId`/`nodeType`/`message`/`lastRaw`.
- **Import/export** (`GET /api/schemas/export`, `POST /api/schemas/import`).
  Экспорт отдаёт бандл всех схем; импорт показывает diff
  (created/updated/unchanged) и применяет изменения.

Четыре дефолтные схемы (`buildDefault*Schema`) создаются идемпотентной
seed-миграцией `M001_prompt_templates_to_schemas.ts` (вставка `WHERE NOT EXISTS`,
повторный прогон ничего не ломает).

### Сборка пакета `@tg-games/schema-contract`

Пакет поставляется тремя файлами: `index.mjs` (ESM, **единый источник правды**),
`index.cjs` (CommonJS) и `index.d.ts` (типы). Чтобы `.mjs` и `.cjs` не расходились
вручную, `.cjs` **генерируется** из `.mjs`:

```bash
npm run build:contract        # перегенерировать index.cjs из index.mjs
```

Тест-страж `tests/schema-contract-sync.test.ts` падает в CI, если `index.cjs`
рассинхронизирован с `index.mjs` или если набор экспортов в `.mjs`/`.cjs`/`.d.ts`
разошёлся — это ловит ручную правку одного файла без остальных.

## Медиа: озвучка, иллюстрации (issue #71) и голосовой ввод (issue #118)

Под сообщением-результатом каждого хода (кроме отклонённых ходов) бот прикрепляет
две inline-кнопки: «🔊 Озвучить» (`tts:<stepId>`) и «🎨 Нарисовать иллюстрацию»
(`draw:<stepId>`). По клику исчезает **именно нажатая** кнопка (вторая остаётся),
а сцена приходит **новым** сообщением — голосовым/аудио или фотографией. Текст
сцены берётся из сохранённого шага (`game_steps.changes_summary`), поэтому
озвучить или нарисовать можно и более ранний ход. Медиа доступно только автору
хода (`getStepWithOwner` сверяет владельца сессии); при ошибке генерации кнопка
возвращается, чтобы можно было повторить.

Провайдер выбирается `MEDIA_PROVIDER` (по умолчанию — тот же, что `LLM_PROVIDER`).
Модели по умолчанию подбираются под провайдера и переопределяются переменными
`MEDIA_TTS_MODEL` / `MEDIA_TTS_VOICE` / `MEDIA_IMAGE_MODEL` / `MEDIA_IMAGE_SIZE`:

| Провайдер  | Озвучка (TTS)                                              | Иллюстрации               |
| ---------- | --------------------------------------------------------- | ------------------------- |
| OpenAI     | `gpt-4o-mini-tts` / `alloy` → Ogg/Opus (голосовое)        | `gpt-image-1`             |
| Google     | `gemini-2.5-flash-preview-tts` / `Kore` → PCM в WAV (аудио) | `imagen-3.0-generate-002` |
| OpenRouter | не поддерживается (кнопки не показываются)                | не поддерживается         |
| Azure      | не поддерживается (задайте `MEDIA_PROVIDER=OPENAI/GOOGLE`) | не поддерживается         |

Возможность необязательна и включается **мягко**: фабрика `createMediaProvider`
возвращает `null`, если ключ пуст (`MEDIA_API_KEY`, иначе ключ LLM-провайдера),
если `MEDIA_ENABLED=false`, все под-возможности выключены или провайдер не
поддерживает медиа (OpenRouter/Azure). При `null` кнопки не показываются, голос
не распознаётся, и игра работает как обычная текстовая. Отдельно отключить
озвучку, картинки или распознавание речи можно флагами
`MEDIA_TTS_ENABLED` / `MEDIA_IMAGE_ENABLED` / `MEDIA_STT_ENABLED`.

### Голосовой ввод действий (issue #118)

Если у игрока есть **активная игра**, присланное голосовое сообщение
распознаётся в текст (STT) и сразу выполняется как игровое действие — отвечать
можно голосом, не печатая. Бот скачивает аудио из Telegram в память, передаёт
его STT-провайдеру и **нигде не сохраняет**: ни на диск, ни в БД (в памяти
буфер живёт только на время распознавания). Распознанный текст показывается
игроку и проходит обычный игровой ход. Модели STT по умолчанию: OpenAI →
`whisper-1`, Google → `gemini-2.5-flash`; переопределяются `MEDIA_STT_MODEL`.
Без активной игры или при `MEDIA_STT_ENABLED=false` бот просит написать действие
текстом.

Пользователь может отправить `/config`, выбрать «Озвучка» или «Иллюстрации»,
затем модель и параметр: голос для TTS либо размер/соотношение для изображения.
Настройки сохраняются в `user_media_configs` и применяются к следующим кликам
«Озвучить»/«Нарисовать иллюстрацию». Если настройки нет или выбранное значение
больше не доступно для текущего `MEDIA_PROVIDER`, бот использует значения из
переменных `MEDIA_TTS_MODEL` / `MEDIA_TTS_VOICE` / `MEDIA_IMAGE_MODEL` /
`MEDIA_IMAGE_SIZE`.

## Web-админка (issue #114)

Локальный запуск:

```bash
npm install                 # один установочный проход на весь монорепозиторий
npm run migrate
npm run dev:admin:backend   # NestJS API (apps/admin-api)
npm run dev:admin:frontend  # Vite + React (apps/admin-web)
```

Frontend открывается на `http://localhost:5173`, backend API — на
`http://localhost:3001/api`. Для входа введите имя в Telegram в формате `@name`
(регистр и ведущий `@` не важны) пользователя, у которого в таблице `users`
стоит `is_admin = TRUE`; backend найдёт его по `username`, отправит код через
`ADMIN_AUTH_BOT_TOKEN` или, если он не задан, через `SUPPORT_ADMIN_BOT_TOKEN`.
После подтверждения frontend хранит Bearer-токен в `localStorage`.

Навигация по разделам отражается в URL через hash-маршрут
`#/<раздел>/<сущность>?<фильтры>` (issue #152). Например,
`#/sessions/s-42?userId=u-1` открывает раздел «Сессии» с выбранной сессией
`s-42` и фильтром по пользователю `u-1`. Благодаря этому работают закладки,
расшаренные ссылки и кнопки браузера «Назад»/«Вперёд», а перезагрузка страницы
не сбрасывает состояние на раздел по умолчанию. Логика разбора и сборки хеша
лежит в `apps/admin-web/src/adminRoute.ts` и покрыта тестами
`apps/admin-web/tests/admin-route.test.ts`.

Проверки приложений админки:

```bash
npm run typecheck -w apps/admin-api
npm test -w apps/admin-api
npm run typecheck -w apps/admin-web
npm run build:admin
```

| Провайдер  | Переменные ключа/endpoint | JSON Mode |
| ---------- | ------------------------- | --------- |
| OpenAI     | `OPENAI_API_KEY`          | `response_format: { type: "json_object" }` |
| Google     | `GOOGLE_API_KEY`          | `responseMimeType: "application/json"` |
| OpenRouter | `OPENROUTER_API_KEY`      | `response_format: { type: "json_object" }` |
| Azure      | `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_VERSION` | `response_format: { type: "json_object" }` |

Для `LLM_PROVIDER=AZURE` значение `LLM_MODEL_NAME` должно быть именем deployment
в Azure OpenAI. Версия API по умолчанию — `2024-10-21`, её можно переопределить
через `AZURE_OPENAI_API_VERSION`.

### Алиасы моделей Azure для расчёта стоимости (issue #120)

В Azure OpenAI в качестве имени модели используется имя deployment (алиас),
которое пользователь задаёт сам, поэтому оно не совпадает с ключами справочника
цен `MODEL_PRICING`. Без сопоставления стоимость запроса считалась бы нулевой
(0 миллицентов). Чтобы этого избежать, заведена таблица `azure_models
(alias, model)`: для провайдера `AZURE` перед расчётом расхода миллицентов алиас
резолвится в каноническую модель, по которой и берётся цена.

Сопоставления удобно задать через `AZURE_MODELS` — пары `alias=model` через
запятую; они сидируются в таблицу при старте (`ON CONFLICT DO NOTHING`, поэтому
ручные правки прямо в БД не перезатираются):

```env
AZURE_MODELS=story-deployment=gpt-4o,hints-deployment=gpt-4o-mini
```

Карта кешируется в памяти; правки в таблице подхватываются при перезапуске.
Если алиас не найден, используется само имя deployment (поведение как раньше).

### Глобальные модели по умолчанию (issue #345)

По умолчанию все LLM-запросы идут к провайдеру и модели из `.env`
(`LLM_PROVIDER` / `LLM_MODEL_NAME`), а эмбеддинги — к
`EMBEDDING_PROVIDER` / `EMBEDDING_MODEL`. Раздел «Модели» в админке позволяет
переопределить имена моделей глобально через таблицу `model_defaults`:

| Ключ | Где используется |
| --- | --- |
| `llm_model_name` | все текстовые LLM-запросы Schema Engine и поддержки |
| `embedding_model` | эмбеддинги экспертизы и поиска документов |

Провайдеры не хранятся в БД и выбираются только через `.env`. Медиа-запросы
(озвучка, иллюстрации, распознавание речи) используют свои настройки и этим
разделом не управляются.

Бот и админка — разные процессы, поэтому defaults кешируются с TTL
`MODEL_DEFAULTS_CACHE_TTL_MS` (по умолчанию 30000 мс). После правки в админке
бот подхватит изменения не позже чем через этот интервал. Если значение в БД
отсутствует или временно недоступно, runtime использует fallback из `.env`.

## Как играть

1. `/start` — регистрация, появляется основное меню.
2. **Начать новую игру** → выбор сценария → выбор персонажа (из пресетов с
   инвентарём) → выбор стартовой локации (со своим вводным нарративом).
   Первая игра — бесплатный триал, последующие — **Купить за N ⭐️**.
3. После оплаты (или сразу для триала) создаётся активная сессия, приходит
   вводный текст выбранной локации, меню переключается на игровое. Новая игра
   **не завершает** предыдущие — к ним можно вернуться через «Мои игры».
4. **Действие** — достаточно просто написать сообщение: при наличии активной
   игры любой произвольный текст трактуется как игровое действие. Кнопка
   «Действие» лишь подсказывает, что делать. Под полученным результатом, если
   включено медиа (issue #71), появляются кнопки «🔊 Озвучить» и «🎨 Нарисовать
   иллюстрацию»: по клику кнопка исчезает, а сцена приходит отдельным голосовым
   сообщением или картинкой.
5. **Подсказка** — LLM предлагает 3 варианта одним сообщением: нумерованный
   список действий и ряд кнопок (1, 2, 3) для их выполнения.
6. **Статус** — характеристики персонажа, текущее время мира (сезон, дата,
   время суток) и последний нарратив (тот, что попадёт в промпт следующего хода).
7. **Мои игры** — два сообщения: активные игры (кнопка переключает текущую
   игру и присылает статус) и завершённые игры (кнопка присылает историю ходов).
8. **Помощь** — справка с inline-кнопками «🛟 Служба поддержки» (открывает чат
   с ботом поддержки, если задан `SUPPORT_BOT_USERNAME`) и «Как купить TG
   звёзды» (по клику текст сообщения заменяется ссылкой-инструкцией).

## Служба поддержки (issue #57, #59)

Два отдельных Telegram-бота поверх той же БД, что и игровой бот:

- **Клиентский бот** (`botSupport`). Любое сообщение клиента попадает в его
  открытое обращение — если открытого нет, создаётся новое.

  **LLM-консультант первой линии** (issue #59): пока обращение не передано
  администратору, на сообщения отвечает «🤖 Бот СП». Он либо помогает сам, либо
  задаёт уточняющие вопросы, а когда собрано достаточно сведений (или клиент
  просит живого человека) — передаёт обращение администратору со
  скомпилированным описанием проблемы. Только после такой передачи (`escalated_at`)
  обращение появляется у администраторов, и все пользователи с флагом `is_admin`
  получают уведомление в боте администраторов. Дальнейшие сообщения клиента
  просто подшиваются в обращение. Консультант отключается флагом
  `SUPPORT_LLM_CONSULTATION=false` — тогда обращение, как раньше, сразу передаётся
  администраторам. При недоступности LLM обращение тоже передаётся администратору,
  чтобы клиент не остался без ответа.

  **Экспертиза через эмбеддинги** (issue #147): консультант работает в три стадии.
  Стадия 1 — по диалогу и последнему сообщению модель формулирует проблемы клиента;
  по их эмбеддингам (провайдер `EMBEDDING_PROVIDER`, модель `EMBEDDING_MODEL`,
  по умолчанию `text-embedding-3-small`) через косинусную близость pgvector
  подтягиваются до `SUPPORT_EXPERTISE_TOP_K` справочных документов. Стадия 2 — эти
  документы подставляются в промпт консультанта (плейсхолдер `{{expertise}}`),
  и бот отвечает клиенту либо сигнализирует, что данных достаточно. Стадия 3 — при
  готовности компилирует чёткую формулировку проблемы для специалистов, которая
  попадает в обращение. Документы экспертизы (заголовок, контент, поисковые фразы)
  редактируются в админке в разделе «Экспертиза»; при сохранении фраз backend
  пересчитывает их эмбеддинги. Для Azure OpenAI дополнительно задаётся
  `AZURE_OPENAI_EMBEDDING_DEPLOYMENT`; deployment должен быть совместим по
  размерности с `EMBEDDING_MODEL`. В аудите LLM-запросов видно, какие документы
  были подтянуты по векторам во время диалога. Если провайдер эмбеддингов не
  настроен, экспертиза просто отключается — консультант работает по старой схеме.

  > 📐 Этот же механизм экспертизы перенесён в игровой процесс (отдельная
  > экспертиза на каждую игру, разгрузка системного промпта от ситуативных
  > правил) — см. фазу 0 в разделе «Возможности» выше и план
  > [docs/expertise-for-games.md](docs/expertise-for-games.md) (issue #154).

  > 🕸️ Альтернативы и надстройки над этим RAG развиты отдельно: граф знаний
  > с ручной разметкой и обходом подграфа — концептуальная онтология
  > [docs/conceptual-ontology-plan.md](docs/conceptual-ontology-plan.md)
  > (issue #323); автоматическое построение графа из документов экспертизы и
  > обзорные (глобальные) запросы по сводкам сообществ — Graph RAG
  > [docs/graph-rag-plan.md](docs/graph-rag-plan.md) (issue #328, реализован в
  > #334). Сравнение «когда что выбирать» — в разделе «Игровой процесс» выше.
- **Бот администраторов** (`botSupportAdmin`). Реагирует только на
  администраторов (`users.is_admin = TRUE`); сообщения от остальных молча
  игнорируются. Команда `/topics` показывает активные обращения inline-кнопками
  с датой и цветным статусом:
  - 🔵 — обращение ещё не открывалось этим администратором;
  - 🔴 — есть новые сообщения клиента;
  - ⚪️ — новых сообщений нет.

  Клик по обращению делает его текущим для администратора, присылает
  непрочитанные сообщения клиента и сдвигает отметку прочтения. Любой текст
  администратора уходит в его текущее обращение, сохраняется в БД и доставляется
  клиенту, создавшему обращение.

  Команда `/users` (issue #62) показывает список пользователей inline-кнопками.
  Если пользователей больше 10 — список листается кнопками `◀️`/`▶️` в том же
  сообщении. Клик по пользователю выводит там же список его игр (с такой же
  пагинацией), а клик по игре — её последний статус и кнопку «📥 Скачать историю
  ходов», присылающую все ходы игры текстовым файлом.

Стартовые администраторы задаются в `SUPPORT_ADMIN_IDS` (их `telegram_id` через
запятую) — при запуске бота администраторов им проставляется `is_admin`.

Запуск стека поддержки (профиль `support` в `docker-compose.yml`):

```bash
docker compose --profile support up --build
```

Локально (каждый бот — отдельный процесс, БД общая):

```bash
npm run dev:support          # клиентский бот
npm run dev:support:admin    # бот администраторов
```

> Боты поддержки используют тот же `.env`, что и игровой бот, поэтому при их
> запуске должны быть заданы и общие переменные (`TELEGRAM_BOT_TOKEN`, ключ
> LLM-провайдера, параметры БД).

## Тесты

```bash
npm test
```

Покрыты юнит-тестами (с мок-провайдером LLM, без сети и БД):

- извлечение/валидация JSON от LLM и санитизация лимитов;
- ретраи редуктора при невалидном ответе и сообщение о «нестабильном мире»;
- ход через Schema Engine (issue #178, #238): дефолтная `action`-схема повторяет
  пять фаз (нарратив + инвентарь, характеристики, флаги, остальные данные),
  суммирование стоимости всех узлов, сохранение `cacheKey` между ретраями
  (`tests/schema-reducer-router.test.ts`, `tests/cache.test.ts`,
  `tests/credits.test.ts`); при отсутствии активной схемы — `MissingActiveSchemaError`;
- время мира (issue #65): нормализация `world_time` у старых сессий, продвижение
  времени суток и календарной даты, формат строки времени в статусе;
- точные часы ЧЧ:ММ (issue #67): нормализация и арифметика времени, согласование
  `time_of_day` с точным `time`, миграция старых сессий «только с time_of_day»;
- завышение характеристик, game over, обрезка инвентаря;
- фабрика провайдеров и загрузка конфигурации;
- манифесты сценариев и шаблоны промптов в БД, сборка промптов через шаблоны;
- служба поддержки (`tests/support.test.ts`): статусы топиков и их символы,
  клавиатуры и подписи обращений, тексты обоих ботов, кнопка «Служба поддержки»;
- LLM-консультант первой линии (`tests/support-llm.test.ts`, issue #59): промпты
  и роли диалога, парсинг решения бота, эскалация при сбое LLM, маркировка «Бот СП»;
- экспертиза через эмбеддинги (`tests/support-expertise.test.ts`, issue #147):
  блок справочных материалов, парсинг стадий 1/3, оркестрация определения проблем
  и компиляции обращения, объединение результатов векторного поиска по топ-K;
- экспертиза в игре (issue #154): выделение ключей ситуации и сборка блока
  (`tests/game-expertise.test.ts`), scope-фильтр по `game_id`
  и идемпотентный сид базы знаний (`tests/expertise-repo.test.ts`); подстановка
  документов выполняется узлами схемы (контекст `embeddingProvider`/`expertiseTopK`);
- долговременная память игры (issue #166): сборка блока памяти, отбор ячеек,
  парсинг извлечения и логика «хрониста» (`tests/memory.test.ts`),
  репозиторий ячеек (`tests/memory-repo.test.ts`) и удаление памяти при отмене
  хода (`tests/cancel-step.test.ts`); инъекция памяти и извлечение фактов
  выполняются узлами схемы (контекст `memoryCells`/`memoryTopK`);
- просмотр данных по играм (`tests/admin-users.test.ts`): пагинация списков,
  клавиатуры пользователей/игр, карточка игры и обработчики команды `/users`;
- медиа сцены (issue #71): юнит-тесты клавиатуры по возможностям провайдера,
  упаковки PCM→WAV и фабрики `createMediaProvider` (`tests/media-units.test.ts`);
  интеграционные тесты колбэков (`tests/media-callbacks.test.ts`) — прикрепление
  кнопок к результату, удаление **только** нажатой кнопки и отправка голоса/фото,
  проверка владельца сцены, недоступность медиа и возврат кнопки при ошибке;
- отчёт тестировщику по медиа (issue #75, `tests/tester-media-report.test.ts`):
  форматирование отчёта (запрос/ответ/ошибка/токены), утилиты `media/trace`
  (`clipForReport`, `normalizeUsage`) и интеграция — отчёт приходит тестировщику
  после озвучки/иллюстрации и при ошибке API, обычному игроку — нет.
